# Tower of Time — план превращения MVP в стильную игру

Стек фиксирован (`AGENTS.md`): A-Frame 1.7.1 + `@c-frame/physx@0.3.0`, plain `<script>`, jsDelivr, без сборщиков/TS/npm. Работаем микро-шагами, каждый шаг — отдельный коммит с чек-листом. Ассеты (GLB, HDR, PNG-панели) делает пользователь по спецификации в конце этого документа; код пишется на заглушках-примитивах и подхватывает реальный арт через config.

## Принципы реализации

- Каждая фаза дробится на микро-шаги в `CURRENT_TASK.md` по ходу, тут — каркас и цель.
- Везде, где трогаем незнакомый PhysX-API (joint pose, kinematic-переключение) — сначала диагностический шаг (`Object.keys`/`typeof`) по правилу `AGENTS.md` п.13.
- Геймплейные числа — только в `js/config.js`. Новые сущности — отдельные компоненты в `js/components/`.
- Реальные ассеты подставляются через config-поля (`model`, `hdri`, `image`) — заглушка ↔ арт без переписывания логики.

## Глоссарий (закрепляем понятия)

- **Поле времени (купол)** — `room-fog-dome` + `room-dome-collider`. Граница игровой зоны, cyan-энергия.
- **Ядро** — бывший `pedestal`. Обломок машины, на нём слоты сборки.
- **Деталь (важная)** — бывшие цветные кубы. Нужны для механизма. Тип/локация/слот задаются в config.
- **Мусор** — бывшие серые кубы. Помехи, в слоты не снепятся.
- **Опасный объект** — бывший `red-ball`. При попадании в сборку — ломает её.
- **Кусок железа** — бывший `ball-bat`. Отбивать опасные объекты.
- **Механизм** — набор слотов + требуемых деталей. Сборка механизма = разблокировка перехода/победа.
- **Локация (комната)** — самостоятельная «комната» (прошлое/настоящее/будущее и, в будущем, любые новые уровни). Своя HDR-картинка, свой уровень опасности, свой набор деталей. Игрок входит/выходит сколько угодно раз, пока есть время, и переносит любое число предметов между комнатами. Количество локаций — произвольное (≥3), задаётся данными, не хардкодом.
- **Маршрут сборки** — настраиваемый граф: какой собранный механизм разблокирует какую локацию. Зависит от числа уровней, описывается данными и легко перестраивается при добавлении локаций.
- **Перенос (carry)** — состояние принадлежности предмета локации; при переходе предметы могут «ехать» с игроком и оставаться в другой комнате.

## Фаза 0 — Модель данных и глоссарий в config (фундамент, без смены поведения)

Цель: единый контракт, на котором стоят все фазы. Поведение игры пока не меняется.

- В `js/config.js` добавить декларативные структуры (пока с тестовыми значениями, дублирующими текущие 5+6 кубов). **Всё — как списки/словари произвольного размера, без числа «3» в логике:**
  - `CONFIG.parts` — список деталей `{ id, kind: 'mechanism'|'junk', model, homeLocation, mechanism, slot }`. `homeLocation` — где деталь изначально спавнится; её можно унести в другую комнату.
  - `CONFIG.locations` — **массив/словарь произвольной длины**, каждая локация: `{ id, label, hdri, fogTint, hazardLevel, partIds[] }`. Стартовая локация помечается флагом `start: true`.
  - `CONFIG.mechanisms` — словарь механизмов `{ id, requiredPartIds[], slots: [{ id, position, rotation, acceptPartId }] }`. Требуемые детали механизма могут принадлежать **разным локациям** (вынуждает переносить предметы).
  - `CONFIG.progression` — **граф маршрутов**: список рёбер `{ unlocksLocation, requiresMechanism }` + `finalMechanism` (запуск машины = победа). Меняя/дополняя этот список, добавляем новые локации и маршруты без правок кода.
  - `CONFIG.assembly` — `{ snapPosTolerance, snapRotToleranceDeg, breakImpulse }`.
- Текущие 3 локации (будущее/прошлое/настоящее) — это лишь **начальное наполнение** массивов; движок не должен предполагать ровно 3.
- Документировать поля комментариями. Не подключать к рантайму на этом шаге.

## Фаза 1 — Снеп-сборка (keystone-механика)

Цель: заменить «стек кубов» на «снеп деталей в слоты схемы». Геометрия пока — примитивы.

- Новый компонент `js/components/assembly-core.js`: держит слоты (из `CONFIG.mechanisms`), отрисовывает призрачную схему (эволюция `ghost-tower-hint.js`).
- Снеп: при `release` детали (хук в `floating-cube.js`/`physx-grab.js`) проверяем близость к подходящему слоту (поз+ориент допуск из `CONFIG.assembly`). Если попали — деталь становится **kinematic** и встаёт в точную позу слота (стабильнее joint-а; снеп без дрейфа).
- Удержание связки: грабнутую снепнутую часть можно поднять как единое целое (v1 — опционально; базовая версия: снеп только к фиксированному ядру).
- Слом: при `contactbegin` опасного объекта со снепнутой деталью — снять kinematic, вернуть dynamic + `breakImpulse`, деталь снова летает.
- `victory-check.js` → переписать в **проверку «все слоты механизма заполнены»** (вместо геометрии стека). Событие `victory`/`mechanism-complete`.
- `ghost-tower-hint.js` → **призрак слотов** (wireframe/полупрозрачные модели в позах слотов).
- Диагностический шаг: проверить переключение dynamic↔kinematic у `rigidBody` в текущем биндинге до боевого кода.

- Решить судьбу маленького купола над ядром (`dome-visual` + `dome-builder` + `dome-collider`): либо убрать визуал и оставить невидимую «зону сборки», либо рестайл. Вынести в отдельный микро-шаг с подтверждением.

## Фаза 3 — Слои мира (глубина VR)

Цель: мир из 3 слоёв, как на 2-й картинке.

- **Слой 2 (вне купола):** новый компонент `js/components/outside-scenery.js` — расставляет дома (заглушки-боксы → GLB) по кругу за куполом.
- **Туман по полу** вне купола: плоскость/объёмный туман-шейдер у пола (отдельный компонент или расширение fog-dome).
- **Слой 3 (HDR-фон):** `world-hdri-sky.js` уже грузит `.hdr`/`.jpg` — подставить комикс-HDR из `assets/hdri/`. Согласовать тон фона с локацией (Фаза 4).

## Фаза 3.5 — Взаимодействие с деталями (руки + сборка)

Цель: стабильный хват и визуал **до** art-pass снеп-схемы. Снеп и GLB-детали тестируем на **готовых** магнитных руках — иначе после смены якоря хвата придётся перегонять tolerance, бросок, биту и hardcore.

**Порядок обязателен: 3.5A → 3.5B.**

### 3.5A — Магнитные руки (первым)

Лор: на руках магниты; grip = заряд, отпустил = разряд, без захвата.

- **Якорь магнита:** дочерний entity `#leftMagnet` / `#rightMagnet`; коллайдер и joint `physx-grab` на tip, не на origin руки. Offsets в `CONFIG.player.hands`.
- **Модель:** GLB с видимым магнитом (`assets/models/leftHandMagnet.glb`, `rightHandMagnet.glb`) — Y-up, метры, low-poly PBR.
- **VFX:** `hand-magnet-vfx.js` — emissive/кольцо при `gripdown`, off при `gripup`.
- **Ввод:** захват **только grip** (trigger — UI/меню, не grab).
- **Бита:** `ball-bat.attachToHand` → поза/скорость магнита, не корня `#leftHand`.
- **Критерий:** деталь стабильно на конце магнита; release предсказуем; Quest QA без регрессий меню/биты.

### 3.5B — Сборка и детали (после 3.5A)

- **Геометрия схемы:** пересчитать `CONFIG.mechanisms.slots` относительно центра сферы/колец (не «верх стола»).
- **GLB-детали:** `CONFIG.parts[].model` → загрузка вместо куба; PhysX box по bounds.
- **Призраки слотов:** силуэт/wireframe **под форму детали**, не один `slotSize` для всех.
- **Состояния визуала:** floating, ghost, snapped, snapped_active (механизм «ожил»), broken (слом от шара).
- **Критерий:** магнитом поднёс → release → снеп; призраки читаемы на фоне cyan-кольца; Quest FPS OK.

**Не делаем в 3.5:** `location-manager` (Фаза 4), перенос между комнатами, intro-comic.

## Фаза 4 — Локации-комнаты (data-driven, N штук) и прыжки во времени

Цель: произвольное число локаций-комнат со свободным входом/выходом, переносом предметов и настраиваемым графом маршрутов. Никакого хардкода на «3».

- Новый `js/location-manager.js` управляет всем из `CONFIG.locations` / `CONFIG.progression`:
  - `activeLocationId`, `unlockedLocationIds` (стартовая — по флагу `start`), `travelTo(id)` (только для разблокированных).
  - **Персистентное состояние каждой комнаты:** для каждой локации хранится текущее положение/состояние её предметов (летает / снепнута / унесена). Выход и повторный вход в комнату восстанавливает её состояние, а не переспавнивает заново.
- **Перенос предметов между комнатами:** предмет имеет поле «в какой локации сейчас находится». При `travelTo` предметы, которые игрок «забрал с собой» (механика переноса — см. открытые решения), меняют принадлежность на новую локацию и появляются там; остальные остаются в покинутой комнате в своём состоянии. Унести можно любое число предметов.
- **Граф маршрутов из данных:** разблокировка локации происходит по событию «механизм собран» согласно рёбрам `CONFIG.progression` (`requiresMechanism → unlocksLocation`). Добавление новой локации/уровня = дополнение `CONFIG.locations` + `CONFIG.progression`, без правок логики.
- **UI перехода на ядре:** список 3D-кнопок строится **динамически** по числу локаций (заблокированные — неактивны/скрыты). При большом числе локаций — прокрутка/страницы (заложить в компонент сразу).
- Смена локации меняет HDR-фон (Фаза 3), туман и `hazardLevel` (Фаза 5).
- Спавнеры (`spawn-floating-cubes.js` и др.) переводятся на «спавн набора деталей конкретной локации по её `partIds`», управляются `location-manager`.
- Победа — по `finalMechanism` из `CONFIG.progression`: событие `machine-launched` → финал.
- Начальное наполнение (для проверки графа): старт FUTURE → механизм активации PAST открывает PAST; детали present-механизма лежат в PAST и FUTURE (нужно переносить) → сборка открывает PRESENT → финальный механизм и запуск = победа. Это лишь данные, движок остаётся N-локационным.

## Фаза 5 — Опасности, отбивание, таймер петли

Цель: давление времени и нарастающая угроза.

- `red-ball.js` → «опасный объект»: число/скорость растут с глубиной прохождения (`location.hazardLevel`).
- `ball-bat.js` → «кусок железа»: рестайл-модель, та же механика отбивания.
- **Таймер петли:** обратный отсчёт «окно времени схлопывается»; истёк — поражение/рестарт. UI-таймер в стиле комикса; пауза по `time-scale` учитывается.
- Экран поражения (эволюция `victory-ui.js`).

## Фаза 6 — Меню и настройки в стиле комикса

Цель: пауза по кнопке контроллера + комикс-оформление.

- Кнопка контроллера → пауза/меню поверх игры (новое состояние в `game-lifecycle`).
- Рестайл `game-menu.js` и `victory-ui.js` под комикс (PNG-арт фона/кнопок вместо плоских canvas-плашек).
- Настройки: громкость, сложность, рестарт, выход.

## Фаза 7 — Вступительный анимированный комикс (в конце)

Цель: заставка как в UNDERDOGS из нарезанных пользователем панелей.

- Новый компонент `js/components/intro-comic.js`: слоистые PNG-панели на плоскостях перед камерой; анимации пан/зум/parallax/появление через `THREE`/A-Frame `animation`.
- Раскадровка: учёный → запуск машины → прыжок в прошлое → попытка в будущее → столкновение → разлёт деталей (мостик в геймплей).
- Скип по кнопке; по завершении → переход в первую локацию (FUTURE).

## Спецификация форматов ассетов (делает пользователь)

- **3D-детали и дома:** glTF Binary `.glb`, один файл со встроенными текстурами, Y-up, масштаб в метрах. Детали ~0.08–0.12 м. Low-poly. PBR (metalness/roughness). Origin (0,0,0) — в точке снепа/опоры. Папка `assets/models/`.
- **Руки с магнитами:** GLB на руку + видимый магнит на конце; origin запястья/tracker; tip калибруется через `CONFIG.player.hands` (local pos/rot) или empty в Blender.
- **HDR 360-фон:** equirectangular 2:1. Предпочтительно Radiance `.hdr` (парсер уже есть) либо `.jpg`. Разрешение 2048×1024 (для Quest достаточно). Папка `assets/hdri/`.
- **Панели комикса (заставка):** `.png` с альфа-каналом, sRGB. Для parallax — каждый план панели (передний/средний/задний) отдельным PNG. Папка `assets/comic/`.
- **Арт меню/UI:** `.png` с альфа (фон панели, кнопки, иконки). Папка `assets/ui/`.
- **Звук (опционально, позже):** `.mp3`/`.ogg` в `assets/audio/`.

## Что переиспользуем без изменений

- `time-scale.js` (SUPERHOT), `physx-grab.js` (joint на магнит после 3.5A), `desktop-ui-cursor.js` (прицел), `collisionLayers`-реестр, `room-dome-collider` как граница.

## Открытые решения (подтвердить по ходу)

- Судьба маленького купола над ядром (Фаза 2).
- **Магнитные руки (3.5A):** калибровка tip — только config vs empty в GLB; trigger на руке — только UI.
- Снеп: только к фиксированному ядру (v1) vs поднимать собранную связку целиком (стретч).
- **Механика переноса предметов между комнатами (Фаза 4):** как именно «взять с собой» произвольное число вещей в VR (2 руки) — например, переносной лоток/стеллаж на ядре, который едет с игроком, либо «всё, что снепнуто на ядре, путешествует вместе с ядром», либо персональный инвентарь. Выбрать на старте Фазы 4.
- Точная раскадровка комикса (Фаза 7) — после геймплея и визуала.

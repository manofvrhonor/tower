# AGENTS.md — Правила агента

Читается перед каждым ответом. Пользователь — **не программист**: не читает код, не различает рабочий код и выдуманный. Все правила учитывают это.

---

## 1. Контекст

- `PROJECT_LOG.md` — стек, решения, история. Подключается по запросу через `@`.
- `CURRENT_TASK.md` — текущий микро-шаг. Подключён всегда.
- Перед действием сверься с обоими.
- Стек физики и захвата зафиксирован в `PROJECT_LOG.md` (раздел «Разворот с Cannon на PhysX»). Не менять без явного запроса пользователя.

---

## 2. Формат ответа

- Начинай с **TL;DR** (2–3 строки): что делаю / что нужно от пользователя.
- Дальше — основной ответ.
- Язык: русский. Маркдаун. Код — в блоках с указанием языка.

---

## 3. Простой язык

- Не используй термины без пояснения в скобках.
- Описывая код — говори, **что произойдёт для игрока**, а не как устроено внутри.

---

## 4. Не выдумывать

- Не придумывай API, методы, версии, имена компонентов.
- Не уверен — скажи прямо: «нужно свериться с README» и попроси пользователя открыть страницу.
- Особо: имена и параметры компонентов `@c-frame/physx` (`physx-body`, `physx-grabbable`, `hand-grab` и т.п.) — только из README `github.com/c-frame/physx`.

---

## 5. Перед каждым куском кода

Сообщи **до** кода:
1. Что код делает (1–2 строки, для игрока).
2. В какой файл (точное имя).
3. Куда вставлять (конец файла / после строки X / заменить блок Y).
4. Как пользователю проверить, что сработало.

Без этих 4 пунктов код не выдавать.

---

## 6. Микро-шаги

- Один ответ = одно проверяемое изменение.
- Не давай правок в нескольких файлах в одном ответе.
- После шага — стоп-точка: «Сохрани файл, перезагрузи Chrome (или localhost в Quest через Quest Link), должен увидеть X. Напиши, что получилось».
- Не двигайся дальше без подтверждения.

---

## 7. План перед действием

Для всего, кроме мелочей (цвет, текст, число):
1. Сначала — **план списком, без кода**.
2. Жди «ок».
3. Реализация по одному пункту.

Сомневаешься, нужен ли план — давай план.

---

## 8. Один чат — один микро-шаг

- Контекст между чатами живёт в `.md`-файлах, не в истории сообщений.
- Не пытайся «вспомнить» — читай файлы.

---

## 9. Working Context

В `CURRENT_TASK.md` есть категории: **ИЗВЕСТНО / НЕИЗВЕСТНО / ПРЕДПОЛОЖЕНИЯ / РЕШЕНО**.

- Появился новый факт/вопрос/решение — предложи правку: «Добавить в Working Context, раздел X: …».
- Файл правит **только пользователь**.

---

## 10. Не задавать повторных вопросов

- Если ответ есть в чате или в `.md`-файлах — не спрашивай.
- Не помнишь — скажи: «Не нахожу ответ, повтори, пожалуйста».

---

## 11. Правки `.md`-файлов

- `PROJECT_LOG.md`, `CURRENT_TASK.md`, `AGENTS.md` правит **только пользователь**.
- Ты предлагаешь текст. Не переписываешь молча.
- Большая правка (несколько разделов / весь файл) — выдавай **файл целиком одним блоком**, для замены через Ctrl+A.

---

## 12. Запреты

- Без новых фреймворков, библиотек, зависимостей без обсуждения.
- Без изменений структуры папок и ключевых файлов без обсуждения.
- Не трогать файлы из «НЕ трогаем» в `CURRENT_TASK.md`.
- **Не возвращать** `super-hands` и `@c-frame/aframe-physics-system` (Cannon).
- CDN — **только** `https://cdn.jsdelivr.net/`. Никаких `aframe.io`, `unpkg.com` и т.п.

Подробности — `PROJECT_LOG.md`, разделы «Технологический стек» и «Архитектурные решения».

---

## 13. Безопасность изменений

- Если правка может сломать рабочее — предупреди в TL;DR: «⚠️ Это трогает X. Если сломается, восстановим из коммита».
- Большая правка → сначала «скопируй файл в `.backup`».
- Не предлагай удалять файлы/папки без явного предупреждения.
- Миграция Cannon → PhysX: каждое изменение в `index.html` — отдельным коммитом, для точечного отката.

---

## 14. Тестируем локально, не Netlify

- Цикл: правка → сохранить → `npx serve` уже запущен → перезагрузить вкладку Chrome → если нужно VR — войти через Quest Link.
- **Деплой Netlify не предлагать** после микро-шагов. Только в конце этапа или по запросу пользователя.
- Если нужна публичная HTTPS-ссылка (тест в Quest Browser напрямую, без Quest Link) — явно сказать «это требует деплоя» и спросить разрешение.

---

## 15. Если что-то пошло не так

Не угадывай. Спроси у пользователя:
1. Что произошло (словами).
2. Что должно было произойти (словами).
3. Скриншот, если видно на экране.
4. Текст ошибки (объясни, как открыть консоль: F12 → Console, скопировать красное).

Один диагностический шаг → ответ → следующий. Не списком сразу.

**PhysX-специфика:** если `.wasm` не грузится — попроси полный лог консоли + вкладку Network (F12 → Network, фильтр `physx` и `wasm`). Не предлагать «другую версию» наугад.

---

## 16. Завершение задачи

Когда микро-шаг готов:
1. TL;DR: «Шаг X.Y готов. Проверь: [действие]. Если работает — двигаемся дальше».
2. Если закрыт целый шаг из `PROJECT_LOG.md` — предложи правки в него (что сделано / где мы / следующий шаг / запись в историю сессий).
3. Жди от пользователя: «двигаемся дальше» или новый `CURRENT_TASK.md`.
4. **Не предлагай `git push` и деплой автоматически.** Можно напомнить «накопилось N коммитов, не забудь push для бэкапа», но не настаивать.
